# Своя база каждому приложению: что сделано и что осталось (волны DB-A/B/C)

Ветка `feat/db-per-app-land` (перенос волн DB-A/B/C, снятых с `feat/db-a-sandbox-fullstack`).
Дата приземления: 2026-07-30. Номера миграций при переносе изменены — см. раздел
«Переномер» ниже, иначе следующий инстанс будет искать несуществующие файлы.

## ✅ Сделано

- **DB-A**: fullstack-профиль собирается настоящим `next build` без `output: "export"`.
- **DB-B**: fullstack проходит проверку целостности — модель может писать API-роуты и
  серверный код; `static`-профиль по-прежнему это бракует (регрессия исключена).
- **DB-C**: платформа выдаёт приложению СВОЮ схему и СВОЮ роль в Postgres. Изоляция
  держится на правах Postgres, а не на секретности строки подключения.

Ключевые файлы: `backend/src/lib/app-profiles.ts`,
`backend/src/services/app-database.service.ts`,
`backend/src/services/app-database-binding.ts`,
`backend/src/migrations/101_app_databases.ts`,
`backend/scripts/verify-app-db-isolation.ts`.

## 🟡 Ограничения (не решены, но известны)

### 1. Docker Desktop не работает на dev-машине
`Docker Desktop is unable to start` (Windows 11 / WSL). Значит песочница
(`sandbox.service.ts`) не проверена в Docker-сценариях: изоляция роли, `--network none`,
лимиты памяти/CPU верифицированы **только на голом Postgres вне Docker**.
Решение: прогнать гейт на машине с живым Docker.

### 2. Railway-верификация fullstack остаётся `static`/`skipped`
Сборка fullstack **на Railway** не проверена, как и доступность выданной базы из
рантайма. Это отдельная волна **DB-D** (рантайм-хостинг серверной части).

### 3. `APPS_DATABASE_URL` пуст
Переменная документирована в `backend/.env.example`, значения нет. В staging/prod
провижининг вернёт `not-configured`, и fullstack-приложения баз не получат. Открыть
Postgres на узлах — задача инстанса osgard-infra; после этого задать переменную в Railway.

### 4. Нет UI восстановления кредов
`GET /projects/:id/database` отдаёт креды только владельцу проекта. Отдельной страницы
«забыл пароль от базы» нет — нужно сказать пользователю на витрине генератора, что креды
возвращаются на странице проекта.

## ⚠️ Почему отказы честные, а не спрятанные

Волна намеренно построена на видимых отказах вместо имитации успеха:

- `APPS_DATABASE_URL` не задан → провижининг отвечает `not-configured`, а не «успех»;
- кластер недоступен → ошибка логируется, но **генерация приложения не падает**
  (приложение создаётся без базы);
- `db/schema.sql` невалиден → сохраняется `schema_status: "failed"`, ошибка видна в отчёте.

Это не идеальное решение — идеальным было бы гарантировать базу каждому приложению, — но
оно не выдаёт отсутствие базы за наличие.
