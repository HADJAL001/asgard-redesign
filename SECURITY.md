# Безопасность OSGARD

Этот документ описывает модель безопасности проекта OSGARD (`asgard-redesign`):
что уже внедрено, как это активировать/эксплуатировать и какие задачи ещё
открыты. Ответственный за инициативу безопасности — выделенная роль «Security»
(изолированная ветка `feature/security`, короткие PR по блокам).

> В этом файле НЕТ секретов, токенов и учётных данных — только имена
> переменных окружения и процедуры. Никогда не коммить реальные значения.

## Блок 3 — Двухфакторная аутентификация (2FA)

- TOTP (RFC 6238) через `speakeasy`; QR для настройки в приложении-аутентификаторе.
- **Логин требует второй фактор.** При `twofa_enabled` `POST /auth/login` не выдаёт
  токены по одному паролю: возвращает `{ twofaRequired: true }` (HTTP 200, без
  токенов). Клиент повторяет запрос с `twofaToken` (TOTP) или `backupCode`.
- **Резервные коды** — 10 одноразовых кодов, выдаются один раз при активации; в БД
  хранятся только SHA-256-хеши. Перевыпуск: `POST /auth/2fa/backup-codes/regenerate`.
- **Секрет 2FA шифруется в покое** (AES, `ENCRYPTION_KEY`). Старые открытые секреты
  читаются прозрачно (обратная совместимость).
- **Rate-limit** на `/auth/2fa/verify` — 10 попыток/мин (защита от брутфорса кода).

Роуты: `POST /auth/2fa/{setup,verify,disable}`, `GET /auth/2fa/status`,
`POST /auth/2fa/backup-codes/regenerate`.

## Блок 4 — Аудит действий администратора

- Таблица `admin_logs` расширена: `ip`, `user_agent`, `status` (миграция 069).
- `recordAdminAction()` — ручная запись богатого события (смена роли/бана/начисление)
  с IP и User-Agent.
- `adminAuditMiddleware` — **автоматический предохранитель**: логирует ЛЮБОЙ
  админ-запрос (в т.ч. read-only доступ к PII и новые ручки, которые забыли обложить
  ручным логом). Дедуп с ручной записью.
- Клиентский IP берётся из левого адреса `X-Forwarded-For` (приложение за прокси).
- Просмотр — вкладка «Журнал» в админке (колонка IP, UA в подсказке).
- Не смешивать с финансовым `audit_log` (`lib/audit.ts`) — у него другое назначение.

## Блок 1 — Certificate pinning (мобильный клиент)

Библиотека `react-native-ssl-public-key-pinning` (OkHttp CertificatePinner на
Android, TrustKit на iOS). После инициализации все `fetch`/XHR к боевому хосту
проверяют публичный ключ сертификата → защита от MITM с подменой сертификата.

Реализация: `mobile/lib/ssl-pinning.ts`, вызов в `mobile/app/_layout.tsx`.

**Fail-safe:** пиннинг НЕ активируется, пока не заданы оба пина из env и хост не
`https`. Поэтому dev-сборки и период до выпуска прод-сертификата не ломаются.

### Активация (после привязки домена и выпуска сертификата)

1. Снять base64 SHA-256 хеш публичного ключа (SPKI) боевого сертификата:
   ```
   openssl s_client -servername <host> -connect <host>:443 </dev/null \
     | openssl x509 -pubkey -noout \
     | openssl pkey -pubin -outform der \
     | openssl dgst -sha256 -binary | openssl enc -base64
   ```
2. Снять **backup-пин** — со второго/следующего сертификата или промежуточного CA.
   iOS (TrustKit) требует **не менее двух пинов**, иначе init бросит исключение.
3. Задать env для EAS-сборки:
   - `EXPO_PUBLIC_SSL_PIN_PRIMARY` — основной пин
   - `EXPO_PUBLIC_SSL_PIN_BACKUP` — резервный пин
   - `EXPO_PUBLIC_API_URL` — `https://<боевой-хост>`
4. Собрать **кастомный dev/prod build** (EAS) — в Expo Go пиннинг не работает.
5. Проверить: подмена сертификата (прокси-перехват) должна ломать запросы;
   нарушение логируется в Sentry (`SSL pinning violation`).

> Ротация сертификата без обновления пинов «окирпичит» клиент — всегда держите
> валидный backup-пин и обновляйте пины заранее (можно через OTA `expo-updates`).

## Блок 2 — Активная кибероборона

### Прикладной уровень (внедрено)

`backend/src/middleware/threat-defense.ts`:

- **Honeypot-ловушки** (`/.env`, `/wp-login.php`, `/phpmyadmin`, …) — легитимный API
  их не содержит; запрос = достоверный вредоносный сигнал. Попадание мгновенно
  блокирует IP, ответ — нейтральный 404.
- **Скоринг угроз** — per-IP очки с окном 10 мин (Redis + in-memory fallback);
  порог 10 → авто-блок на 1 час.
- **`ipBlocklistGuard`** — ранний middleware, отсекает заблокированные IP (403).
- Авто-блок → алерт в Sentry.

`recordOffense(ip, reason, weight)` можно вызывать и из других мест (например, на
серии неудачных логинов) — по умолчанию подключены только honeypot'ы (ноль ложных
срабатываний).

### Инфра-уровень — привязка домена + Cloudflare (runbook, требует доступа к аккаунтам)

Цель: поставить Cloudflare (WAF + anti-DDoS + управляемые правила) перед трафиком.

1. **Vercel (фронтенд):** Settings → Domains → добавить `osgard.com`.
2. **DNS у регистратора** перевести на Cloudflare (сменить NS на выданные Cloudflare),
   зона Cloudflare — proxied (оранжевое облако):
   - `A`/`CNAME` фронта → Vercel (`cname.vercel-dns.com`).
   - Поддомен API (например `api.osgard.com`) → Railway-хост, тоже proxied.
3. **Cloudflare:** SSL/TLS = Full (strict); включить WAF Managed Rules, Bot Fight
   Mode, rate limiting rules; при необходимости — «Under Attack Mode».
4. **Backend:** переключить мобильный/веб-клиент на `https://api.osgard.com`.
5. **`trust proxy`:** т.к. трафик идёт через Cloudflare→Railway, включить доверие
   прокси в Express (`app.set('trust proxy', ...)`), чтобы `req.ip` = реальный
   клиент. ⚠️ Сейчас НЕ включено — см. «Открытые задачи» (влияет на корректность
   rate-limit и honeypot-блокировок по IP).
6. После привязки — снять пины сертификата и активировать Блок 1.

## Блок 5 — Автоматическое сканирование безопасности

- `.github/workflows/security-scan.yml`:
  - `npm audit` по `root`/`backend`/`mobile` (полный отчёт + гейт по `critical`);
  - **CodeQL** (JS/TS, `security-and-quality`);
  - **gitleaks** — поиск случайно закоммиченных секретов.
  - Триггеры: PR, push в `main`, еженедельно (регулярный пентест-цикл).
- `.github/dependabot.yml` — еженедельные PR обновлений зависимостей (3 пакета +
  GitHub Actions).

### Известные уязвимости (бэклог npm audit на момент внедрения)

Гейт по `critical` пока **advisory** (`continue-on-error`), чтобы не блокировать все
PR из-за незакрытых транзитивных уязвимостей. План: чинить через Dependabot, затем
сделать гейт блокирующим.

- **mobile** — `tar` (critical, path traversal) через `expo-splash-screen`;
  всего ~25 (в т.ч. high). Обновлять по мере выхода фиксов Expo.
- **backend** — `rpc-websockets` → уязвимый `uuid` (high); всего ~8.
- **root** — ~9 (high/moderate, без critical).

Проверять актуальный список: `npm audit` в каждом пакете.

## Обязательная конфигурация для продакшена (секреты)

Задать в env (Railway/Vercel), НЕ полагаться на дефолты в коде:

| Переменная | Назначение | Риск дефолта |
|-----------|------------|--------------|
| `JWT_SECRET` | подпись access-токенов | дефолт `default_secret` → подделка токенов |
| `JWT_REFRESH_SECRET` | подпись refresh-токенов | дефолт → подделка refresh |
| `ENCRYPTION_KEY` | AES для email/2FA-секретов | слабый дефолт → расшифровка при утечке БД |
| `REDIS_URL` | rate-limit / threat-defense / кеш | без него — только in-memory (не шарится между инстансами) |

## Открытые задачи (action items)

1. **Отозвать скомпрометированный `EXPO_TOKEN`.** Токен робота Expo дважды попадал
   в чат и один раз в вывод команды — считать скомпрометированным. Отозвать на
   expo.dev → Access tokens и перевыпустить. (См. HANDOFF.md.)
2. **Задать сильные `JWT_SECRET` / `JWT_REFRESH_SECRET` / `ENCRYPTION_KEY`** в проде
   (см. таблицу выше). Теперь это принудительно: `assertProductionSecrets()`
   (`lib/security-preflight.ts`) при `NODE_ENV=production` **не даст серверу
   стартовать** с незаданным/дефолтным/коротким секретом. Задайте значения в env
   Railway — иначе прод-инстанс не поднимется.
3. **Включить `trust proxy`** после Cloudflare — иначе rate-limit и IP-блокировки
   работают по адресу прокси, а не реального клиента (все клиенты в одном «ведре»).
4. **Расчистить бэклог npm audit** (critical/high) и сделать гейт блокирующим.
5. **Активировать certificate pinning** после привязки домена и выпуска сертификата.
6. **Провести первый ручной пентест** после привязки домена (внешняя поверхность).
